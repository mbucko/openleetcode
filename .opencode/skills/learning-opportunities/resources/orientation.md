# Repo Orientation: openleetcode (CS3704 fork)

> Generated by orient. Re-run to update.

## One-line purpose
A local, offline LeetCode-style practice tool that builds and runs a user's solution against `.test` files for a set of shipped problems, so you can practice algorithms without an internet connection.

## Primary language(s)
- **Python** — the CLI harness that orchestrates everything (`src/app/`), plus the Python solution runner.
- **C++** — the primary solve language and the fully end-to-end path, including the test harness (`data/languages/cpp/`).
- **JavaScript (Electron)** — an optional desktop UI (`src/ui/`) that wraps the CLI.

(No TypeScript, despite `package.json` files.)

## Pipeline / workflow stages
1. **Install** — `install.py` (via `install.sh`/`install.bat`) copies `data/` + `src/app/` + the results schema into `install/OpenLeetCode/`.
2. **Select problem & language** — `openleetcode.py` parses args and resolves the problem dir, language template dir, testcases dir, and build dir.
3. **Scaffold** — missing language template files are copied into the problem's language folder; for C++, `functionextractor.py` reads the user's `solution.cpp` and writes `solutionfunction.h` naming the solution method.
4. **Build** — C++ only: CMake configures/builds/installs two binaries (`solution_cpp`, `solution_expected_cpp`). Python skips the build and uses a shared runner script.
5. **Run tests** — `testrunner.py` invokes the binary/runner once with the testcase dir, an output `.results` path, and a testcase name (`All` or a specific one).
6. **Produce results** — the runner executes each `.test` case and writes a JSON results file.
7. **Validate & report** — `testrunner.py` enriches the JSON with `stdout`/`stderr`, `resultsvalidator.py` checks it against `results_validation_schema.json`, and `logger.py` prints a summary.

## Key files
- `src/app/openleetcode.py` — CLI entry point and orchestrator; wires every stage together. | Read first: it is the map of the whole system.
- `src/app/testrunner.py` — runs the built binary/python runner, writes the `.results` file, and reports failures. | Explains the test execution contract and the results-file lifecycle.
- `src/app/functionextractor.py` — regex-extracts the C++ solution method name into `solutionfunction.h`. | Small but central to how the C++ harness knows what to call.
- `src/app/resultsvalidator.py` — loads and applies the JSON schema to results. | Shows the contract the UI and CLI both depend on.
- `install.py` — build/install script that defines source vs. installed layout (with optional UI packaging). | Explains why you edit `data/` but run `install/`.
- `data/languages/cpp/problemtest.cpp` — the C++ test harness: reads `.test` files, binds args, compares outputs, writes JSON. | The reference implementation of the test format.
- `data/languages/cpp/binder.h` — template metaprogramming that derives the solution's argument types and invokes it. | The cleverest/hardest part of the C++ side.
- `data/languages/python/problemtest.py` — the Python equivalent harness (type-hint-driven parsing, tree handling). | Best place to see the `.test` contract without metaprogramming.
- `src/schema/results_validation_schema.json` — schema all `.results` files must satisfy. | Reveals required fields for Success/Failed/Skipped cases.
- `src/ui/index.js` — Electron renderer: editor, problem selection, run/save commands, results rendering. | Shows how the UI drives the CLI and consumes results.

## Core concepts
**problem_builds layout**: Each problem lives under `problems/<Name>/` with a `description.md`, per-language folders (`cpp/`, `python/`), and a shared `testcases/` folder. Language runtimes/templates live separately under `languages/<lang>/`. Defined by the directory math in `openleetcode.py` and mirrored in `directory-manager.js`.

**`.test` file format**: One argument per line, expected result on the last line; a final line of `*` means "skip comparison" (used for custom testcases that just print output). Parsed in `problemtest.cpp`, `problemtest.py`, and written by the UI's custom-testcase flow.

**User vs. expected solution**: `solution.cpp`/`solution.py` is the blank the learner fills in; `solution_expected.cpp`/`solution_expected.py` is the reference answer. The C++ build compiles both (`EXPECTED` macro selects which in `solutionwrapper.h`); `--run-expected-tests` runs the reference.

**Results JSON + schema validation**: All runs emit a JSON file (`status`, `duration_ms`, `tests[]`, plus `stdout`/`stderr`). `resultsvalidator.py` enforces the schema so the UI can render results uniformly regardless of language.

**Source vs. installed tree**: You edit `data/problems/` and `data/languages/` in the repo; the installer copies them into `install/OpenLeetCode/`. Edits to the installed copy are lost on reinstall.

## Common gotchas
- **Edit `data/`, not `install/`.** The README describes the installed `problems/` tree; in this fork your source of truth is `data/problems/`. Reinstalling overwrites the installed copy.
- **There is a typo'd duplicate.** `resultsvalidator.py` defines `validateResults` twice (the second definition wins); the first silently never runs its schema-not-set guard.
- **`--list-problems` exits with status 1** (`sys.exit(1)`) even on success, so scripts that check exit codes can misread it.
- **Python solutions need full type hints** on parameters and return, or `problemtest.py` raises. The C++ path instead relies on `functionextractor.py` finding a `public:` method — a solution with no public method fails extraction.
- **A hard 3-second timeout** (`PROBLEM_LTE_S` in `testrunner.py`) kills hanging solutions.
- **`TestCase11test`** (missing the dot) in some problem folders is never picked up as a testcase.
